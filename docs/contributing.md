# 小组协作规则

依据小组开发规则：统一 Docker 环境；所有正常开发在功能分支进行；各人修改自己负责的模块；谁开发、谁测试；组长审核后合并 main。群昵称采用“姓名 + 任务号”，例如“周建行 1”。

## 分支

- 公共环境：`common/<内容>`；当前初始草案使用 `common/phase0-bootstrap`。
- 2 号：`feat/distributed`。
- 3 号：`feat/hdfs`。
- 4 号：`feat/yarn-mapreduce`。
- 5 号：`feat/standalone-pseudo`。
- 6 号：`feat/wordcount`。
- 7 号：`feat/mergefile`。
- 独立修复：`fix/<问题>`；跨模块修改：`cross/<内容>`。

按一个可验证功能或问题逐次增量修改、测试和提交。提交说明使用 `<类型>(<模块>): <具体内容>`。新增公共接口、公共代码、跨模块变更需在 `.changes/` 写明原因、影响模块、接口变化、测试与回滚方式；不允许混入无关的基础环境升级。

## 测试与 PR

先运行基础环境验证，再运行本模块实际构建、启动、核心功能、结果验证及受影响模块回归。PR 写明修改范围、接口变化、实际执行的命令与结果、尚未通过的项目。测试失败或运行待验证时保留草案，不能合入稳定 main。

本机无 Docker 时可以做静态检查并保存工作区草案，不能宣称模块完成或打稳定标签。当前仓库初始为空，暂不存在稳定版本；基础镜像实际通过测试并经组长审核后，再形成首个稳定提交与 `v0.1-bootstrap` 标签。不要为了创建 PR 向 main 塞入未经验证的内容。

## 冻结与回滚

后续基于稳定标签开发；公共环境升级采用新镜像标签，不覆盖稳定镜像。发布时记录镜像 ID；多人共享可通过镜像仓库 digest 引用，或组长导出同一份镜像让成员导入。

公共变更合并后如需回退，在修复分支使用 `git revert <提交号>` 并提 PR，不强推、不重写 main 历史。恢复旧镜像时同时恢复相应契约与配置版本。

## 验收材料

每位成员负责自己模块的实验说明、测试结果、PPT、含字幕配音的视频及讲解。组长负责环境与总览部分；PPT 和视频制作属于后续阶段。
